# Автоматизированная публикация допущенного занятия

**Единственный источник учебных текстов** — закрытый GitHub `slobodatablichka/gos-exams-2027`. Публичный `slobodatablichka/gos-exams-2027-public` хранит только страницы сайта. Не копируйте 18 статей вручную.

## Однократная настройка доступа

В настройках **публичного** репозитория создайте два Actions secrets, каждый с отдельным fine-grained GitHub token, ограниченным **одним** репозиторием:
- `PUBLICATION_SOURCE_TOKEN`: доступ только к закрытому `gos-exams-2027`, **Contents — Read-only**.
- `PUBLICATION_PR_TOKEN`: доступ только к публичному `gos-exams-2027-public`, **Contents — Read and write**, **Pull requests — Read and write**.

Разделение прав важно: у fine-grained token одинаковые разрешения для всех выбранных репозиториев. Один токен с разным уровнем доступа к двум репозиториям настроить нельзя. **Не публикуйте токены** в файлах, логах и сообщениях. Настройка считается проверенной только после реального успешного запуска.

Для создания PR с автоматическим запуском CI используется этот токен, а не штатный `GITHUB_TOKEN`, поскольку созданные им PR обычно не запускают события `pull_request`. Репозиторий должен разрешать создание PR автоматикой. Дальнейшие проверки проводятся на PR отдельно; workflow ничего не объединяет и не размещает на Pages самостоятельно.

## Один запуск на занятие

Публичный GitHub → **Actions** → **Prepare approved lesson publication PR** → **Run workflow**. Укажите `lesson` (например `15`) и `source_ref` (по умолчанию `main`; для воспроизводимости предпочтителен проверенный SHA закрытого репозитория).

Workflow:
1. Проверяет секрет и номер, извлекает публичный и закрытый репозитории.
2. Запускает тесты генератора и контроль существующего сайта.
3. Проверяет допуск каждой темы (`sources/l3/l2/l1=done`, `quality=approved`) по **закрытому журналу**, проверяет полные формулировки и все исходники.
4. Делает **dry-run**, затем одним запуском `--apply` формирует 18 страниц и все служебные страницы, ссылки, анонс и реестр.
5. Проверяет сохранение старых URL и создаёт или обновляет **один PR** с полной публикацией.

Далее требуются: `pull_request` CI `completed/success` и прочитанный `PASS`; объединение PR; CI `main` и Pages; этап 8 — фактическая проверка URL и обновление `site=published` в закрытом журнале. **Успешная сборка сама по себе не меняет `site`.**

## Защиты и ограничения

- Если нет одного из двух секретов, допуска или любого файла L3/L2/L1 — **остановка до записи**.
- Если занятие уже зарегистрировано как опубликованное — генератор отказывает, старые URL не перезаписываются.
- Служебные ссылки `../l3/qNN.md`, `../l2/qNN.md`, `../l1/qNN.md` превращаются в публичные `qNN-l3.html`, `qNN-l2.html`, `qNN-l1.html`; неизвестные `.md`-ссылки вызывают отказ.
- Формы `**Официальный вопрос:**`, `**Официальная формулировка:**` и историческая форма `> **Официальный экзаменационный вопрос.**` поддерживаются.
- Особая рабочая публикация занятия 13 регулируется отдельным адресным исключением; стандартный допуск для прочих занятий не ослабляется.
- Старые страницы и ссылки проверяются штатным `publish-lesson.py check` и интеграционным `test-publish-lesson.py`. CI не заменяет проверку доступности Pages.

## Контроль токенов и результата

Для экономии токенов в обычной работе читать итог workflow, строку `PREPARED`, строки `PASS`, номер PR, commit SHA и ошибки при наличии. Не загружать в ИИ всю книгу, 18 HTML-страниц или целые журналы GitHub Actions без конкретного сбоя.

### Надёжная отправка ветки (04.11.2026)

Проверочный workflow №41815552576 дважды завершился ошибкой GitHub `Internal Server Error` при `git push` через `PUBLICATION_PR_TOKEN`, **после** успешного чтения обоих репозиториев, quality gate, dry-run и полной генерации. Для отделения операции записи ветки от операции создания PR используются два независимых средства авторизации: `branch-token: ${{ github.token }}` (временный штатный токен GitHub Actions, `contents: write` только в публичном репозитории) и `token: ${{ secrets.PUBLICATION_PR_TOKEN }}` (создание PR, инициирующее обычный CI). Секреты остаются прежними, пересоздавать их не нужно. Переключение считается доказанным только после реального успешного запуска; прежний успех генератора не подменяет подтверждения отправки ветки.
